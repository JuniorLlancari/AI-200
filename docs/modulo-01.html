1

Store and manage containers in Azure Container Registry

El "almacén" de imágenes: dónde viven, cómo se organizan, cómo se versionan y cómo se construyen en la nube.

Ver módulo en Microsoft Learn ↗

¿Qué es ACR?

Un registro Docker privado y administrado. A diferencia de Docker Hub, da control directo de acceso, geo-replicación y se integra nativo con AKS, Container Apps y App Service.

TierPara qué
BasicDev/aprendizaje — throughput y storage limitados
StandardMás storage/throughput para producción
PremiumGeo-replicación, private endpoints, content trust

Jerarquía: Registry → Repository → Artifact

Registry — el servidor/cuenta en sí, URL única <nombre>.azurecr.io
Repository — una carpeta por nombre de imagen (ej. inference-api); soporta namespaces con "/" (ej. produccion/inference-api)
Artifact — una combinación imagen:tag concreta (ej. inference-api:v1.0.0)

Los namespaces sirven para control de acceso: un equipo puede tener permiso de push solo dentro de su propio namespace.

Tags, Layers y Manifests

  • Layers — cada instrucción del Dockerfile crea una capa; ACR las deduplica entre imágenes (ej. varias imágenes basadas en python:3.11 comparten esa capa, ahorrando storage).
  • Manifest — lista las layers + configuración de un artifact; se identifica por un digest SHA-256 inmutable.
  • Tag — referencia legible y mutable; un mismo artifact puede tener varios tags (ej. v1.2.0 y stable apuntando a la misma imagen).

Direccionar: por tag vs por digest

Por tag

Legible, cómodo en desarrollo. No garantiza reproducibilidad — el tag puede haberse movido.

Por digest

Inmutable — garantiza que todos los nodos corren exactamente la misma imagen. Clave en producción.

docker pull myregistry.azurecr.io/inference-api@sha256:0a2e0185...

ACR Tasks: el "CI/CD" del registry

Un motor de build que corre dentro de Azure: envías el código fuente (carpeta local, repo Git o tarball remoto) y ACR construye + pushea la imagen, sin necesitar Docker local.

Quick Task

Ejecución única bajo demanda. Equivale a docker build + push, pero en la nube.

Task con trigger

Recurso persistente disparado por: commit/PR en Git, actualización de la imagen base (ej. parche de seguridad en python:3.11), o schedule (cron).

Multi-step Task

Workflow en YAML: build → push → correr tests dentro del contenedor, antes de dar la imagen por válida.

La variable {{.Run.ID}} genera un tag único por ejecución, para trazar qué build produjo qué imagen:

az acr build --registry myregistry --image inference-api:v1.0.0 .

Estrategias de tagging y versionado

Tags estables

Ej. latest, v1 — se reutilizan; cómodos, pero distintos nodos pueden terminar corriendo imágenes distintas.

Tags únicos

Ej. v1.2.0-build456 — nunca se reusan; garantizan reproducibilidad y trazabilidad para auditoría.

Semantic versioning (MAJOR.MINOR.PATCH): mayor = cambio incompatible, menor = feature nueva compatible, patch = fix. En producción, evitar latest — usar tags explícitos.

Bloqueo y limpieza

Una imagen en producción se puede bloquear para que nadie la borre ni sobreescriba por accidente:

az acr repository update -n myregistry -t app:v1 --write-enabled false

Cuando un tag estable se reapunta, la imagen anterior queda "huérfana" (sin tag) pero sigue ocupando espacio. acr purge limpia esas imágenes sin tag más viejas que X días — se puede agendar como una Task recurrente. En tier Premium existen además políticas de retención automáticas.

2

Deploy containers to Azure App Service

Del registry a una app corriendo de verdad: cómputo, autenticación, runtime, configuración, despliegue seguro y diagnóstico.

Ver módulo en Microsoft Learn ↗

App Service Plan vs Web App

Plan = el "servidor" (CPU/RAM) donde corren una o más apps. El SKU define el nivel (ej. B1 Basic, económico pero sin autoscale). Para contenedores Linux, el plan debe ser Linux.

Web App = el recurso que efectivamente corre tu imagen — apunta a un registry/repositorio:tag concreto.

Origen de la imagen

Azure Container Registry

Recomendado en producción: integra Managed Identity, geo-replicación y escaneo de imágenes.

Otros registries

Cualquier registry HTTPS compatible con Docker Registry API v2 (Docker Hub, GHCR, self-hosted) — requiere server URL + usuario/contraseña para imágenes privadas.

Autenticación a ACR

Managed Identity

System-assigned (vive y muere con la app) o user-assigned (recurso independiente, reutilizable en varias apps). Requiere rol AcrPull sobre el registry. Recomendado en producción.

Admin credentials

Usuario/contraseña del ACR (az acr update --admin-enabled true). Más simple para dev, pero credenciales que rotar a mano.

Desplegar y actualizar

az webapp create -g rg -p plan -n app \ --container-image-name myregistry.azurecr.io/app:v1

Actualizar a una versión nueva cambia solo el tag configurado — App Service reinicia y hace docker pull solo:

az webapp config container set -g rg -n app \ --container-image-name myregistry.azurecr.io/app:v2

Ojo: si reusás el mismo tag (ej. latest), App Service no detecta el cambio solo — hay que reiniciar manualmente o activar Continuous Deployment (--enable-cd true), que crea un webhook disparado cuando ACR publica una imagen nueva.

Runtime: comando de inicio y puerto

Se puede sobreescribir el CMD del Dockerfile con un comando de arranque custom (ej. para correr migraciones antes de levantar la app):

az webapp config set -g rg -n app \ --startup-file "gunicorn --bind=0.0.0.0:8000 app:app"

Si el contenedor no escucha en el puerto 80/8080, hay que decirle a App Service a dónde mandar el tráfico con WEBSITES_PORT:

FrameworkPuerto típico
Node.js (Express)WEBSITES_PORT=3000
Python (Gunicorn)WEBSITES_PORT=8000
Java (Spring Boot)WEBSITES_PORT=8080
ASP.NET CoreSin cambios (usa 80)

Almacenamiento persistente

Por defecto, escribir en el filesystem del contenedor es efímero — se pierde en cada restart. Activando WEBSITES_ENABLE_APP_SERVICE_STORAGE=true, el path /home persiste entre restarts y se comparte entre todas las instancias si la app escala horizontalmente.

Always-on y Health Checks

Sin always-on, la app se descarga de memoria tras ~20 min sin requests — el próximo request sufre un cold start. Requiere tier Basic (B1) o superior.

healthCheckPath — App Service pega esa ruta cada minuto; tras varios fallos seguidos (10 por defecto) saca la instancia del balanceo. Tu endpoint debería devolver 200 solo si la app está realmente lista para servir tráfico.

App settings, connection strings y Key Vault

App settings se inyectan como variables de entorno normales, encriptadas en reposo. Para bases de datos, las connection strings llevan un prefijo especial según el motor:

TipoPrefijo de env var
SQL AzureSQLAZURECONNSTR_
MySQLMYSQLCONNSTR_
PostgreSQLPOSTGRESQLCONNSTR_
CustomCUSTOMCONNSTR_

Para secretos con rotación/auditoría, un app setting puede ser una referencia a Key Vault (@Microsoft.KeyVault(SecretUri=...)) — la app sigue leyendo una variable de entorno normal, sin saber que vino de Key Vault.

Slot settings

App settings normales viajan con el código al hacer swap. Los marcados como slot settings quedan "pegados" al slot (ej. ENVIRONMENT=staging) y no se mueven — así staging no termina creyendo que es producción tras un swap.

Deployment Slots + Swap

Un slot es una copia "hermana" de la Web App con su propio hostname — permite probar una versión nueva sin tocar producción. Requiere plan Standard (S1) o superior.

stagingversión nueva a validar
⇄
productionlo que ven los usuarios

El swap intercambia staging ↔ production sin downtime: si algo sale mal, se puede revertir con otro swap.

Observabilidad y diagnóstico

  • Container logs (stdout/stderr) — activar con --docker-container-logging filesystem, se guardan en /home/LogFiles/.
  • Log stream (az webapp log tail) — logs en vivo de todas las instancias, cada línea identifica de cuál viene.
  • Kudu / SCM (https://<app>.scm.azurewebsites.net) — consola de diagnóstico: variables de entorno resueltas (/Env), explorador de archivos de /home, descarga de un ZIP de diagnóstico.
  • SSH — inspección interactiva dentro del contenedor, si la imagen trae openssh-server configurado en el puerto 2222.
  • Azure Monitor / Log Analytics — para retención larga y consultas KQL sobre logs históricos.
AppServiceConsoleLogs | where Level == "Error" | where TimeGenerated > ago(1h)
