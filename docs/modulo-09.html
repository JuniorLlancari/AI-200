Instrument an app with OpenTelemetry

Estándar abierto para capturar qué hizo un request en cada servicio por el que pasó.

Ver módulo en Microsoft Learn ↗

Los 3 pilares de observabilidad

  • Traces — el camino completo de un request a través de varios servicios.
  • Metrics — números agregados en el tiempo (requests/s, tasa de error).
  • Logs — eventos puntuales con detalle granular.

Metrics te dice que algo cambió, traces te dice dónde, logs te dice por qué.

OpenTelemetry: vendor-neutral

Estándar de la CNCF — instrumentás una vez con las APIs de OpenTelemetry y exportás a cualquier backend compatible (Application Insights, Jaeger, Prometheus...) sin cambiar código. El Azure Monitor OpenTelemetry Distro empaqueta SDK + exporter + librerías de auto-instrumentación en un solo paquete.

Trace y Span

Trace — el recorrido completo de un request (Trace ID único compartido)
Span — una operación puntual (HTTP call, query) con su propio Span ID + parent
Atributos — pares clave-valor con contexto (ej. embedding.model)

La propagación entre servicios usa el header estándar traceparent (W3C) — así todos los spans de todos los servicios quedan bajo el mismo Trace ID.

Setup mínimo

from azure.monitor.opentelemetry import configure_azure_monitor configure_azure_monitor() # lee APPLICATIONINSIGHTS_CONNECTION_STRING

Auto-instrumenta requests, Flask/Django/FastAPI, psycopg2, SDKs de Azure — sin escribir código extra. Cada servicio necesita su propio service.name (+ service.namespace) para aparecer como un nodo distinto en el Application Map; si no, todos se ven como uno solo.

Spans custom para lógica de negocio

La auto-instrumentación no ve tu lógica propia (generar un embedding, ensamblar un prompt). Para eso, spans manuales anidados:

tracer = trace.get_tracer("llm-orchestrator") with tracer.start_as_current_span("GenerateEmbedding") as span: span.set_attribute("embedding.model", "text-embedding-ada-002") embedding = generate_embedding(text)

Anidar with blocks crea la jerarquía padre-hijo automáticamente — sin pasar referencias a mano. SpanKind (SERVER/CLIENT/INTERNAL/PRODUCER/CONSUMER) determina si el span termina en la tabla requests o dependencies.

Analyze app telemetry with logs and metrics

De la telemetría cruda a encontrar la causa raíz: KQL, vistas de Application Insights, dashboards y alertas.

Ver módulo en Microsoft Learn ↗

Tablas clave

TablaGuarda
requestsSpans de servidor (requests entrantes)
dependenciesLlamadas salientes (DB, HTTP, Azure SDK)
exceptionsErrores con stack trace
tracesLogs de la app (logging, ILogger, etc.)

operation_Id (= Trace ID) enlaza todo lo que pertenece al mismo request distribuido; cloud_RoleName identifica el servicio.

KQL: modelo pipe

requests | where timestamp > ago(1h) and success == false | project timestamp, name, resultCode, duration | top 20 by duration desc

has (indexado, rápido) vs contains (substring, más lento) para buscar texto.

Agregar sin engañarse

requests | summarize count(), avg(duration), percentile(duration, 95) by bin(timestamp, 1h), cloud_RoleName

percentile() revela outliers que un promedio esconde. Con sampling activo, usar sum(itemCount) en vez de count() — si no, subestimás el volumen real de eventos.

Correlacionar fallas entre servicios

exceptions | join kind=inner (requests | project operation_Id, requestName=name) on operation_Id

El join por operation_Id conecta una excepción con el request completo que la disparó, cruzando servicios.

Patrones de fallo típicos de IA

  • Timeout de embeddings — spans de dependency con duración fuera de rango o status de error.
  • Cold start de vector search — alta variabilidad justo después de un período sin actividad.
  • Rate limiting del LLM — HTTP 429 en el span de la llamada al modelo; correlacionar con llm.prompt_tokens.

El Application Map señala visualmente qué nodo tiene más latencia/errores; la vista de end-to-end transaction muestra el waterfall completo de un trace puntual.

Dashboards, Workbooks y Alertas — no son lo mismo

Dashboards

Vista estática, "¿está sano el sistema ahora?" — para monitoreo continuo en una pantalla.

Workbooks

Exploración interactiva con parámetros (rango de tiempo, servicio) — para investigar un incidente.

Alertas

Proactivas: log search alert (KQL + umbral) o smart detection (ML, detecta anomalías sin threshold manual).

Un alert rule = scope + condición + action group + severidad (0=Critical a 4=Verbose). Preferir percentiles sobre promedios como condición — un promedio sano puede esconder que el 5% de usuarios sufre latencia alta.
