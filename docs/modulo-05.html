Conectar de forma segura

Microsoft Entra ID

Token OAuth vía DefaultAzureCredential en vez de password — sin secretos de larga duración, auditable.

Password nativo

Usuario/contraseña clásico de Postgres. Guardar en Key Vault, nunca en config.

sslmode=verify-full es lo recomendado en producción — valida que el certificado realmente sea del servidor de Azure, no solo que haya TLS.

PgBouncer integrado

Pooler de conexiones incluido — activarlo y conectar por el puerto 6432 en vez del 5432 directo. Reduce el costo de abrir una conexión nueva por cada request corto.

⚠️ Solo disponible en tiers General Purpose y Memory Optimized — no en Burstable.

Esquema pensado para IA

  • JSONB — metadata flexible (parámetros de modelo, config variable) con operadores propios de consulta.
  • TIMESTAMPTZ — siempre, nunca TIMESTAMP a secas, si tu app cruza zonas horarias.
  • BIGSERIAL vs UUID — serial para IDs secuenciales simples; UUID cuando generás el ID fuera de la DB o mergeás datos de varias fuentes.

Relaciones uno-a-muchos (conversación → mensajes) vía FOREIGN KEY ... REFERENCES; ojo con ON DELETE CASCADE, puede borrar más de lo que pensás.

Patrones SQL propios de Postgres

  • Orden de ejecución: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Por eso un alias definido en SELECT no se puede usar en WHERE (todavía no existe en ese punto), pero sí en ORDER BY.
  • JSONB: -> extrae como JSON, ->> como texto, @> chequea "contiene", ? chequea si existe una key. Los últimos dos usan índices GIN.
  • Keyset pagination: en vez de OFFSET (que escanea y descarta todo lo anterior), filtrar por el último valor visto — rendimiento constante sin importar la página.
  • CTEs recursivas (WITH RECURSIVE) para árboles: hilos de conversación, jerarquías de tareas.
  • INSERT ... ON CONFLICT DO UPDATE (upsert) y RETURNING para traer el ID generado en el mismo round-trip.

SDK: psycopg

Siempre queries parametrizadas (%s), nunca concatenar strings con input de usuario. Para inserts masivos, executemany o COPY (2-10× más rápido que insertar de a uno).

from psycopg_pool import ConnectionPool pool = ConnectionPool(conninfo, min_size=1, max_size=10)

Implement vector search with Azure Database for PostgreSQL

La extensión pgvector convierte tu Postgres en una base vectorial — sin infraestructura aparte.

Ver módulo en Microsoft Learn ↗

Habilitar pgvector

CREATE EXTENSION IF NOT EXISTS vector; CREATE TABLE documents ( id SERIAL PRIMARY KEY, content TEXT, embedding vector(1536) );

La dimensión debe coincidir exacto con la salida de tu modelo (1536 para text-embedding-ada-002, 384 para muchos sentence-transformers).

Operadores de distancia

OperadorMétricaUso
<->L2 (Euclidiana)Cuando la magnitud importa
<=>CosenoEstándar para embeddings de texto
<#>Inner product (negado)Más rápido si tus vectores ya están normalizados

Tipos de dato vectorial

vector

float32 estándar. ~6 KB para 1536 dims.

halfvec

float16 — mitad de storage, casi sin pérdida de calidad.

sparsevec

Solo guarda valores no-cero. Para embeddings dispersos.

Índices ANN: IVFFlat vs HNSW

Sin índice, cada query calcula distancia contra todas las filas (exact search). Un índice aproximado (ANN) sacrifica un poco de recall por velocidad — casi siempre vale la pena.

IVFFlatHNSW
BuildMás rápidoMás lento
MemoriaMenorMayor (~1.5× el tamaño del vector)
Recall90-95%99%+
Tabla vacíaNo soportado (necesita entrenar clusters)Sí, se arma incremental
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);

El operator class del índice debe matchear el operador de la query (vector_cosine_ops ↔ <=>) — si no coinciden, Postgres ignora el índice y hace Seq Scan.

Filtrar + umbral de calidad

Combinar WHERE (categoría, fecha) con la distancia reduce el espacio de búsqueda. Un umbral de distancia evita devolver resultados "parecidos pero irrelevantes" cuando no hay nada realmente similar:

WHERE embedding <=> $1 < 0.4 ORDER BY embedding <=> $1 LIMIT 10

RAG: chunks, citas y evaluación

Separar source_documents de document_chunks (con su propio embedding) permite reconstruir contexto y citar la fuente exacta. Un índice compuesto (document_id, chunk_index) acelera traer "chunks vecinos" para dar más contexto.

Medir calidad: precision (¿lo que trajiste es relevante?), recall (¿trajiste todo lo relevante?), MRR (¿qué tan arriba aparece el primer resultado bueno?) — con un set de preguntas de referencia etiquetadas a mano.

Optimize vector search in Azure Database for PostgreSQL

Configuración de memoria, layout de datos, y cómo escalar cuando un solo servidor no alcanza.

Parámetros de memoria clave

ParámetroPara qué
shared_buffersCache de páginas — debe entrar el índice vectorial
work_memMemoria por operación (sorts) — default 4MB suele quedarse corto
random_page_costBajar a 1.1-1.5 en SSD (default 4.0 asume disco rígido)

Tuning en tiempo de query

SET ivfflat.probes = 10; -- más = mejor recall, más lento SET hnsw.ef_search = 100; -- ídem para HNSW

Confirmar que el índice se usa con EXPLAIN ANALYZE — buscar Index Scan, no Seq Scan.

Metadata: columnas vs JSONB

Para filtros frecuentes (categoría, precio), columnas nativas con B-tree son más rápidas que JSONB. JSONB brilla cuando el esquema es variable — combinar ambos: lo que siempre filtrás, columna; lo dinámico, JSONB.

Particionar tablas grandes

Sobre decenas de millones de filas, particionar por rango (fecha) o lista (categoría) — cada partición tiene su propio índice, y reconstruir uno no bloquea a los demás.

Escalar: vertical, réplicas, cache

Vertical

Subir de tier — más CPU/RAM para cachear el índice completo.

Read replicas

Hasta 5 réplicas de solo lectura; replicación asíncrona (lag de ms a segundos).

Cache (Redis)

Para lookups repetidos (embeddings populares), no para queries de similitud arbitrarias.

Connection pooling: PgBouncer

ModoComportamiento
SessionConexión dedicada toda la sesión — soporta todo, poca ganancia
Transaction (recomendado)Se libera al terminar cada transacción — máxima reducción sin romper casi nada
StatementSe libera tras cada statement — no soporta transacciones multi-statement

En modo transaction, las variables de sesión (SET) no persisten entre transacciones — usar SET LOCAL dentro de cada una. Sumar reintentos con backoff exponencial + jitter para tolerar fallos transitorios de red.
