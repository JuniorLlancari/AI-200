Deploy and monitor applications on Azure Kubernetes Service

De un manifiesto YAML a una API de inferencia corriendo en AKS: desplegar, exponer, configurar con ConfigMaps/Secrets, dar almacenamiento persistente, y diagnosticar cuando algo falla.

Curso: Develop AI cloud solutions on Azure

1. Deploy 2. Configure 3. Monitor

Jerarquía básica de Kubernetes

Deployment — el estado deseado: qué imagen, cuántas réplicas, qué recursos. Vos lo declarás en YAML.
Pod — una instancia en ejecución de ese template. Si muere, el Deployment crea otro.
Container — tu imagen corriendo dentro del Pod.

Un Service no forma parte de esta jerarquía — es el "enrutador" que encuentra Pods por label selector y les da una IP/DNS estable, aunque los Pods mueran y renazcan con otra IP.

1

Deploy applications to Azure Kubernetes Service

Escribir el manifiesto, exponerlo con un Service, aplicarlo al cluster y verificar que arrancó bien.

Anatomía de un Deployment manifest

Un YAML declara el estado deseado: qué imagen correr, cuántas copias, cuánta CPU/memoria, y qué variables de entorno necesita.

apiVersion: apps/v1 kind: Deployment spec: replicas: 2 selector: matchLabels: { app: inference-api } template: metadata: labels: { app: inference-api } spec: containers: - name: api image: myregistry.azurecr.io/inference-api:v1.0 ports: [{ containerPort: 8080 }] resources: requests: { memory: "2Gi", cpu: "1000m" } limits: { memory: "4Gi", cpu: "2000m" }

requests = lo que el Pod necesita para arrancar (Kubernetes lo usa para decidir en qué nodo agendarlo — si no alcanza, el Pod queda Pending). limits = el techo: pasarse de memoria mata y reinicia el Pod (OOMKill); pasarse de CPU solo lo throttlea, no lo mata.

¿Cuántas réplicas?

  • 2 — resiliencia básica, bien para dev.
  • 3 — recomendado para APIs de producción con usuarios externos.
  • 4+ — solo si el tráfico lo justifica; cada réplica extra consume recursos y cuesta.

Si corrés 1 sola réplica y crashea, el servicio queda caído hasta que Kubernetes lo detecte y reinicie.

Secrets en el manifest

Nunca hardcodear API keys en el YAML — se referencian desde un Secret creado aparte:

env: - name: API_KEY valueFrom: secretKeyRef: { name: api-secrets, key: api-key }

Exponer con un Service

ClusterIP (default)

Solo accesible dentro del cluster. Para servicios internos (ej. un vector store que consultan otros workers).

NodePort

Expone un puerto en cada nodo. Útil para pruebas rápidas, poco común en producción.

LoadBalancer

Crea un Load Balancer de Azure con IP pública. Para APIs que sirven usuarios externos.

El selector conecta el Service con los Pods por label — si las labels no matchean, el Service queda sin backend (sin Endpoints), y eso es el bug más común al exponer una app.

spec: type: LoadBalancer selector: { app: inference-api } ports: - port: 80 # lo que usa el cliente targetPort: 8080 # lo que escucha el contenedor

Desplegar, verificar y diagnosticar

kubectl apply -f deployment.yaml -f service.yaml kubectl get pods # READY 2/2, STATUS Running kubectl get svc # EXTERNAL-IP asignada por Azure kubectl logs <pod> --since=10m
SíntomaCausa típica
ImagePullBackOffImagen/tag mal escrito, o el cluster no tiene permiso para pullear del registry
CrashLoopBackOffLa app crashea al iniciar — revisar kubectl logs --previous
Pod en PendingNo hay nodo con CPU/memoria suficiente para los requests pedidos

Configure applications on Azure Kubernetes Service

Externalizar configuración con ConfigMaps, proteger datos sensibles con Secrets, y dar almacenamiento que sobreviva a un restart.

ConfigMaps

Guardan configuración no sensible (feature flags, endpoints) fuera de la imagen — máximo 1 MiB por ConfigMap.

Como env var

Vía configMapKeyRef. Si el ConfigMap cambia, el Pod no se entera solo — necesita reiniciar.

Como archivo montado

Vía volumen. Kubernetes actualiza el archivo en caliente cuando el ConfigMap cambia (excepto con subPath).

Se puede marcar immutable: true para que nadie la edite por error — para cambiarla, hay que borrarla y recrearla.

Secrets

Igual mecánica que un ConfigMap pero para datos sensibles (API keys, connection strings). Tipo Opaque por defecto; también existen tipos especiales para credenciales de registry (dockerconfigjson) y certificados TLS.

kubectl create secret generic app-secrets \ --from-literal=API_KEY="valor-secreto"

Nunca commitear un manifest de Secret con valores literales al repo — se crean directo en el cluster o vía una herramienta externa.

Integración con Azure para secretos

Key Vault CSI Driver

Monta secretos de Key Vault directo como archivos en el Pod. Soporta rotación automática y auditoría detallada.

App Configuration Provider

Genera ConfigMaps/Secrets nativos a partir de App Configuration (que a su vez referencia Key Vault) — gestión centralizada entre varios clusters.

Almacenamiento persistente

El filesystem de un contenedor es efímero por defecto. Una PersistentVolumeClaim (PVC) pide storage con una capacidad y modo de acceso; Kubernetes la enlaza a un PersistentVolume real.

StorageClassBackendModoUso
managed-csiAzure DiskReadWriteOnceUn solo Pod — bases de datos, apps stateful
managed-csi-premiumAzure Disk PremiumReadWriteOnceUn solo Pod, baja latencia (I/O intensivo)
azurefile-csiAzure FilesReadWriteManyVarios Pods a la vez — configs, logs compartidos
azurefile-csi-premiumAzure Files PremiumReadWriteManyVarios Pods, alto rendimiento

Azure Disk usa ReadWriteOnce porque el disco se adjunta a un solo nodo; Azure Files usa ReadWriteMany porque es un share SMB montable desde varios nodos a la vez.

Monitor and troubleshoot applications on Azure Kubernetes Service

Señales clave, herramientas del portal vs kubectl, y un flujo de diagnóstico para pods y Services.

Señales clave para IA

  • Latencia y throughput del endpoint de inferencia
  • Tasa de errores (HTTP 5xx, timeouts)
  • Reinicios de Pod y códigos de salida del contenedor
  • Uso de CPU/memoria vs los requests/limits configurados

Portal vs kubectl

Azure Portal

Live Logs (stream en el navegador), Container Insights (tendencias históricas, heatmaps), Diagnose and solve problems (diagnóstico guiado automático).

kubectl

Consultas puntuales y scripteables: logs, top, describe, exec. Ideal cuando ya sabés qué buscar.

kubectl logs -f <pod> -n ai-workloads kubectl top pods -n ai-workloads

Diagnosticar un Pod

kubectl describe pod muestra el evento que explica el estado: probes fallidas, env vars faltantes, error de pull. Para mirar por dentro sin modificar la imagen:

kubectl exec -it <pod> -- /bin/sh curl http://localhost:8080/health

Diagnosticar un Service

Un Pod sano no sirve de nada si el Service no le manda tráfico. Revisar que el selector matchee las labels del Pod, y que existan EndpointSlices:

kubectl get endpointslices -l kubernetes.io/service-name=inference-api

Para probar un endpoint antes de exponerlo con ingress/LoadBalancer:

kubectl port-forward service/inference-api 8080:80 curl http://localhost:8080/api/inference

Buenas prácticas

  • Empezar visual: portal para una vista rápida de salud antes de bajar a comandos.
  • Labels consistentes: evita el clásico "Service sin Endpoints" por typo en el selector.
  • Probar antes de exponer: port-forward internamente antes de publicar con LoadBalancer/ingress.
  • Logs con contexto: incluir ID de correlación, versión de modelo — ayuda muchísimo a correlacionar con métricas.
