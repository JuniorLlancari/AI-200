Queue and process AI operations with Azure Service Bus

Colas y topics para desacoplar API de procesamiento, con entrega confiable de verdad.

Por qué mensajería en IA

La inferencia tiene latencia impredecible (2s vs 30s para la misma API). Si la API espera de forma síncrona, un pico de tráfico llena el thread pool y todo se cae en cascada. Encolar el request y responder al toque desacopla el ritmo de llegada del ritmo de procesamiento.

Tres patrones clave

  • Load leveling — la cola absorbe picos; los workers consumen a ritmo constante y sostenible.
  • Competing consumers — varios workers en la misma cola, cada mensaje va a uno solo; escalar es agregar workers, sin tocar código.
  • Temporal decoupling — productor y consumidor no necesitan estar online al mismo tiempo (útil durante deploys/reinicios).

Queue vs Topic+Subscriptions

Queue

Un solo consumidor por mensaje. Para un pipeline de procesamiento único (ej. inferencia → guardar resultado).

Topic + Subscriptions

Cada subscription recibe su propia copia — varios servicios reaccionan de forma independiente al mismo evento (notificar, auditar, actualizar dashboard).

Las subscriptions soportan filtros (SQL o por correlación) para enrutar solo los mensajes que le interesan a cada una, sin lógica de filtrado en el consumidor.

Payloads grandes: claim-check

Standard soporta hasta 256 KB, Premium hasta 100 MB. Para documentos/imágenes más grandes, subir el archivo a Blob Storage y mandar por Service Bus solo la referencia (URI) — el mensaje queda liviano y barato de transportar.

El correlation_id sigue al request end-to-end: útil para rastrear una falla a través de API → cola → worker → resultado.

Procesar de forma confiable

Receive-and-delete

Se borra al entregar. Más rápido, pero si el worker crashea a mitad de proceso, el mensaje se pierde.

Peek-lock (default, recomendado)

Se bloquea, no se borra. El consumidor confirma explícito con complete/abandon/dead-letter/defer. Si no confirma a tiempo, vuelve a la cola.

Superado el max_delivery_count (default 10), el mensaje va solo a la Dead-Letter Queue (DLQ) — ahí se investigan fallas sistemáticas en vez de reintentar para siempre. Para tareas largas, AutoLockRenewer extiende el lock automáticamente en vez de que expire a mitad de la inferencia.

Develop event-driven AI workflows with Azure Event Grid

Reaccionar a cambios de estado sin polling — routing de eventos con latencia sub-segundo.

Piezas del rompecabezas

  • Event — notificación liviana ("pasó X"), no el recurso completo.
  • Topics: system (automáticos, de servicios Azure), custom (los creás vos para eventos de tu app).
  • Event subscription — qué eventos de un topic, con qué filtro, van a qué handler.
  • Event handlers — Functions, Service Bus, webhooks, Storage Queues.

Un caso típico: subscribirse a Microsoft.Storage.BlobCreated para disparar un pipeline de embeddings apenas llega un documento nuevo.

Schema: CloudEvents

{ "specversion": "1.0", "type": "com.contoso.ai.InferenceCompleted", "source": "/services/content-moderation", "id": "a1b2c3d4-...", "subject": "/pipelines/moderation/batch-42", "data": { "modelName": "...", "resultLocation": "..." } }

Estándar (CNCF), no propietario de Azure — interoperable con sistemas fuera de Azure. type + source identifican el evento; subject habilita filtrado jerárquico.

Filtrado

  • Por tipo — solo com.contoso.ai.InferenceCompleted, por ejemplo.
  • Por subject — subjectBeginsWith/subjectEndsWith.
  • Advanced filters — sobre el contenido del payload (data.confidence NumberGreaterThan 0.9) para enrutar por umbral de confianza, modelo, o estado.

Entrega, reintentos y confiabilidad

Event Grid espera una respuesta HTTP 200-204 dentro de 30s. Si falla, reintenta con backoff exponencial:

10s → 30s → 1mprimeros reintentos
5m → 30m → 1hsiguen espaciándose
hasta 24hTTL default del evento

Garantiza at-least-once — tu handler puede recibir el mismo evento más de una vez, así que debe ser idempotente (usar el id para deduplicar). Configurar un dead-letter destination (Blob Storage) para no perder eventos que agotan los reintentos.

Build serverless AI backends with Azure Functions

Cómputo bajo demanda: endpoints de inferencia, procesadores de cola, sin gestionar servidores.

Cold start en cargas de IA

Es un evento por instancia, no por request — solo la primera invocación a una instancia nueva lo sufre. En IA se agrava porque las librerías de ML son pesadas de cargar, y encima hay que inicializar clientes/config al arrancar.

Flex Consumption vs Premium

Flex Consumption (default)

Escala por función, memoria configurable (512/2048/4096 MB), always-ready opcional por función para mitigar cold start sin perder el resto serverless.

Premium

Elimina el cold start del todo — siempre hay ≥1 worker precalentado. Para funciones que corren casi continuo.

El límite de 230s

Todo HTTP trigger tiene un timeout de 230s impuesto por el Load Balancer — no depende del plan ni de functionTimeout. Para inferencia larga, patrón async request-reply: la función HTTP encola el trabajo en Service Bus y devuelve 202 Accepted con una URL de estado; otra función (trigger de Service Bus, sin límite de tiempo) hace el trabajo pesado.

Triggers y bindings

  • HTTP trigger — endpoint de inferencia; auth_level controla si necesita key.
  • Service Bus trigger — procesa mensajes; maxConcurrentCalls=1 si cada invocación necesita todos los recursos de la instancia.
  • Output bindings (Blob, Cosmos DB) — guardan resultados sin código de SDK explícito.

Para servicios sin binding (Document Intelligence, Azure OpenAI), se instancia el cliente SDK a nivel de módulo (fuera del handler) para reusar conexión entre invocaciones.

Identidad y acceso

Identity-based connections reemplazan connection strings guardadas: en vez de un secreto completo, solo el endpoint (ej. ServiceBusConnection__fullyQualifiedNamespace) — la Function autentica con su managed identity y el rol RBAC asignado.

Para HTTP, las authorization keys (function/host/system/master) dan una barrera básica de acceso — no reemplazan verificar identidad real del caller (eso lo agrega API Management o Easy Auth).
