Deploy and manage apps on Azure Container Apps

Jerarquía de recursos

Environment — frontera lógica: networking y logging compartidos entre apps (ej. separar dev/test/prod)
Container App — el servicio en sí, apunta a una imagen y expone ingress (externo o interno)
Revision — snapshot inmutable de una configuración; cada cambio relevante crea una nueva
Replica — instancia en ejecución de una revision; las que escalan hacia arriba/abajo

Deploy containers to Azure Container Apps

Cómo crear el entorno, desplegar con CLI/YAML, configurar runtime y autenticación, y verificar que todo arrancó bien.

Ver módulo en Microsoft Learn ↗

Entornos (Environments)

Un environment agrupa una o más container apps que comparten red y observabilidad. No es solo una carpeta: define cómo se comunican internamente las apps y a dónde van los logs.

Ingress externo

API pública, accesible desde internet (ej. un endpoint de inferencia que llama un cliente web).

Ingress interno

Solo alcanzable dentro del environment — para servicios internos que no deben exponerse.

Buenas prácticas: un environment por etapa (dev/test/prod) para reducir el radio de impacto de una revisión mala.

Desplegar: CLI rápido vs YAML

  • az containerapp up — la vía más rápida; puede crear el environment por vos. Ideal para prototipos.
  • az containerapp create — más explícito, útil cuando ya tenés el environment y querés control fino.
  • az containerapp update — actualizar (ej. cambiar imagen) crea una nueva revision, nunca sobreescribe la anterior en caliente.

Con --yaml, el archivo YAML se vuelve la única fuente de verdad (ignora otros flags) — ideal para guardar en control de versiones y revisar cambios como código.

Variables de entorno vs Secrets

Env vars (--env-vars)

Config no sensible: log level, feature flags, URLs de dependencias. Mantiene la imagen portable entre entornos.

Secrets (az containerapp secret set)

Valores sensibles (API keys, credenciales) — se rotan sin tocar la imagen.

Para exponer un secret como variable sin revelar su valor, se referencia con el prefijo secretref::

--set-env-vars EMBEDDINGS_API_KEY=secretref:embeddings-api-key

Autenticación a registries privados

Usuario/contraseña

Rápido de validar, pero implica rotar credenciales manualmente.

Managed Identity (--identity system)

Sin credenciales de larga duración; requiere asignar el rol AcrPull sobre el registry. Preferido en producción.

Verificar el despliegue

  • Logs de consola — errores de arranque, dependencias, crashes de la app.
  • Logs de sistema — problemas a nivel plataforma (no de tu código).
  • Revisions (revision list) — confirmar que el update generó una revision nueva y saludable.
  • Replicas (replica list) — instancias corriendo; útil para detectar scale-to-zero inesperado o crash loops.

Manage containers in Azure Container Apps

Operación del día a día: actualizar imágenes sin romper nada, controlar el ciclo de vida, monitorear y diagnosticar fallos.

Ver módulo en Microsoft Learn ↗

Actualizar imágenes de forma segura

  • Tag (ej. v2) — cómodo pero mutable, puede volver a apuntar a otra imagen.
  • Digest (@sha256:...) — inmutable; en producción permite probar exactamente qué build sirvió cada request.

Cada revision puede estar activa o inactiva. Ante un problema, desactivar es más seguro que borrar: corta el tráfico pero conserva evidencia para investigar. Container Apps purga solas las inactivas pasadas 100 (ajustable con --max-inactive-revisions).

Ciclo de vida de la app

Stop / Start

Acción a nivel de toda la app — garantiza que no arranquen réplicas mientras mitigás un incidente.

Restart

Fuerza reinicio de réplicas para salir de un estado colgado; no reemplaza entender la causa raíz.

Checklist ante una revision que falla: fallo al pull de imagen · puerto mal configurado · variable/secret faltante · probes mal apuntadas · presión de memoria/CPU.

Monitoreo y logs

az containerapp logs show --follow transmite logs en vivo — útil para reproducir un fallo mientras ocurre.

Para que los logs realmente ayuden a diagnosticar, conviene loguear: ID de correlación, ID de revision/build, versión de modelo y desglose de latencia — sin loguear contenido sensible (prompts o documentos completos).

Health Probes

Readiness

"¿Puede esta réplica recibir tráfico ya mismo?" — clave si tu app carga un modelo al iniciar.

Liveness

"¿Sigue viva/sana esta réplica?" — si falla, se reinicia. Demasiado agresiva = más cold starts.

Causas típicas de fallo: puerto o path incorrectos, timeout muy corto para el arranque, o una dependencia externa lenta/caída durante el startup.

Optimizar recursos

Si falta CPU, la réplica se throttlea (más lenta, no muere). Si falta memoria, la réplica se reinicia (falla dura). Son señales distintas para decidir qué subir.

Fijar réplicas mínimas reduce cold starts pero sube el costo base — es un trade-off, no una regla fija.

Scale containers in Azure Container Apps

Cómo Container Apps decide cuántas réplicas correr, basado en HTTP, recursos o eventos — motorizado por KEDA.

Ver módulo en Microsoft Learn ↗

Tipos de reglas de scaling

Toda definición de escalado tiene 3 partes: límites (min/max réplicas), reglas (qué dispara el escalado) y comportamiento (timing). Por defecto: 0 a 10 réplicas si hay ingress. Sin ingress y sin mínimo/regla, la app puede quedar en 0 réplicas sin forma de despertar.

HTTP

Escala por requests concurrentes (umbral por réplica, default 10). Ideal para APIs síncronas.

Escala a 0: sí
TCP

Escala por conexiones concurrentes. Para WebSockets, gRPC, pools de conexión a DB.

Escala a 0: sí
CPU / Memoria

Escala por % de utilización. Para cargas de cómputo pesado (inferencia, transcodificación).

Escala a 0: no
Basado en eventos (KEDA)

Escala por profundidad de cola/lag de eventos. Para workers asíncronos.

Escala a 0: sí

Billing: 0 réplicas = $0 de cómputo · réplica corriendo sin tráfico = tarifa "idle" (más baja) · réplica activa = tarifa completa.

Cómo decide el timing

15sventana HTTP/TCP
30spolling de triggers custom (CPU/eventos)
300scool-down antes de bajar a 0
1→4→8→16…pasos de escalado hacia arriba

Si tenés picos cortos seguidos de calma, ese cool-down de 5 minutos puede mantener réplicas corriendo (y cobrando) más tiempo del esperado.

Scaling basado en eventos — nativos de Azure

KEDA es el motor detrás del escalado por eventos. Estos scalers Azure-native tienen soporte de primera clase:

Azure Service Bus Azure Storage Queue Azure Event Hubs

Ejemplo: con Service Bus, si messageCount = 5 y hay 50 mensajes en cola, KEDA pide 10 réplicas (50 ÷ 5).

--scale-rule-type azure-servicebus --scale-rule-metadata queueName=orders messageCount=5

Preferí managed identity sobre connection strings guardadas como secret — menos rotación manual.

Scalers KEDA para otros workloads

Más allá de Azure, KEDA soporta decenas de fuentes de eventos:

Kafka (lag de consumer group) Redis Lists / Streams Cron (ventanas horarias) Prometheus (métricas custom)

Un patrón útil es combinar Cron (capacidad base en horario pico) con HTTP (para picos inesperados) — cuando hay varias reglas activas, gana la que pide más réplicas.

Recursos de cómputo y perfiles

La memoria debe ser al menos 2× la CPU en GiB (ej. 0.5 CPU → mínimo 1 GiB). Default: 0.25 CPU / 0.5 GiB por réplica.

Consumption

Serverless, pagás por uso, comparte infraestructura. Bueno para tráfico variable.

Dedicated

VMs reservadas, rendimiento consistente. Necesario para GPU o más de 4 CPU / 8 GiB.

Modos de revision y tráfico

Single revision (default)

Solo una revision activa a la vez. Zero-downtime automático: la nueva arranca, pasa sus checks, y recién ahí recibe el tráfico.

Multiple revision

Varias revisions activas a la vez — habilita canary releases, blue-green y A/B testing con reparto de tráfico manual.

Ejemplo — canary release: mandar solo el 20% del tráfico a la v2 para validarla antes de un rollout completo:

v1 · 80%
v2 · 20%

az containerapp ingress traffic set --revision-weight order-api--v1=80 order-api--v2=20

Las revision labels dan una URL fija que siempre apunta a una revision específica, sin importar el reparto de tráfico — útil para que testers validen la v2 antes de sumarla al canary.
