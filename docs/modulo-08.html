Manage application secrets with Azure Key Vault

Almacén centralizado con auditoría, rotación y cifrado — para todo lo que da acceso a un recurso.

Ver módulo en Microsoft Learn ↗

Tres tipos de objeto

Secrets

Strings arbitrarios (hasta 25 KB): API keys, connection strings, tokens.

Keys

Claves criptográficas — la operación (firmar/cifrar) ocurre dentro del vault, la clave nunca sale.

Certificates

X.509 + su clave privada, con emisión/renovación integrada.

Standard tier = protección por software (FIPS 140 L1); Premium = HSM dedicado (FIPS 140-3 L3).

Organización

Un vault por app + entorno (kv-app-dev, kv-app-prod) acota el radio de impacto si uno se compromete. Nombres descriptivos (cosmosdb-connection-string) + hasta 15 tags por secret para filtrar/reportar — pero ojo, cualquiera con permiso de lectura ve los tags, no metas datos sensibles ahí.

Roles RBAC

RolDa acceso a
Key Vault Secrets UserSolo lectura de valores — para la managed identity de la app
Key Vault Secrets OfficerCRUD completo de secrets — para operadores/CI-CD
Key Vault AdministratorTodo el data plane (secrets+keys+certs)
⚠️ Key Vault Contributor es solo control plane (gestiona el recurso vault) — no da acceso a leer secretos.

Recuperar con el SDK

credential = DefaultAzureCredential() client = SecretClient(vault_url=url, credential=credential) secret = client.get_secret("openai-api-key")

DefaultAzureCredential prueba en cadena: env vars → workload identity → managed identity (producción) → Azure CLI (dev local) — mismo código en ambos entornos.

Versionado y rotación

Cada set_secret() con el mismo nombre crea una versión nueva, no sobreescribe. get_secret() sin versión siempre trae la última — rotar es solo guardar una versión nueva y dejar que la app la vuelva a pedir.

Automática con Event Grid

El evento SecretNearExpiry dispara 30 días antes del vencimiento → una Function genera la credencial nueva y la guarda.

Dual-credential

Para servicios con 2 keys activas (Storage, Cosmos DB): generás la nueva, esperás que todas las instancias la usen, y recién ahí revocás la vieja — nunca hay downtime.

Patrón zero-downtime en código: si falla la autenticación contra el servicio downstream, volvés a pedir el secret (trae la versión nueva) y reintentás — sin reiniciar la app.

Soft delete + Purge protection

Soft delete viene activado siempre (7-90 días de retención) — un secret borrado se puede recuperar. Purge protection (opcional) impide el borrado permanente incluso durante ese período — clave en producción para no perder una clave de cifrado para siempre por error o ataque.

Cachear para no saturar Key Vault

Límite: ~4.000 GETs por vault cada 10 segundos. Una app de IA sin cache puede llegar a eso fácil bajo carga. Cache en memoria con TTL corto (15-60 min) reduce eso a un puñado de llamadas por hora, y SecretNewVersionCreated vía Event Grid permite invalidar el cache apenas rota el secret, en vez de esperar el TTL.

Manage application settings with Azure App Configuration

Configuración operativa centralizada, con entornos, feature flags, y un puente transparente a Key Vault.

Ver módulo en Microsoft Learn ↗

Modelo de datos

Key (soporta jerarquía con :, ej. OpenAI:Endpoint) + Value + Label (variante por entorno) + Content-Type (marca JSON o Key Vault reference).

config = load(endpoint=endpoint, credential=DefaultAzureCredential()) model_endpoint = config["OpenAI:Endpoint"]

Labels: mismo key, distinto valor por entorno

Un Pipeline:BatchSize con label Development=10 y Production=200 — la app siempre pide Pipeline:BatchSize, sin lógica condicional. Cargando primero el label nulo (default) y después el label del entorno, las settings específicas sobreescriben solo lo que tienen override, todo lo demás queda en su default.

Feature flags

if feature_manager.is_enabled("UseNewEmbeddingsModel"): process_with_new_model(document)

Casos de uso reales: rollout progresivo de un modelo nuevo, kill switch para apagar un stage que empezó a fallar (segundos, no un rollback de deploy), A/B testing entre dos configuraciones.

Refresh dinámico sin reiniciar

Con un sentinel key vigilado (refresh_on), cambiar ese key dispara que la próxima llamada a config.refresh() recargue toda la configuración — así los cambios se aplican en conjunto, no a medias.

Key Vault references: un solo punto de entrada

App Configuration puede guardar una referencia (URI) a un secret en Key Vault en vez del valor — el load() con keyvault_credential resuelve todo de forma transparente, tu código no distingue de dónde vino cada valor.

config = load(endpoint=endpoint, credential=cred, keyvault_credential=cred) api_key = config["OpenAI:ApiKey"] # resuelto desde Key Vault sin código extra

Requiere 2 role assignments: App Configuration Data Reader en el store + Key Vault Secrets User en el vault. secret_refresh_interval controla cada cuánto se re-resuelve el secreto, independiente del refresh de la config normal.

¿Dónde va cada cosa?

Tipo de datoVa en
Endpoints, nombres de deployment, batch size, timeoutsApp Configuration (directo)
Feature flagsApp Configuration (feature flag)
API keys, connection strings con credencialesKey Vault (referenciado desde App Config)
Certificados TLSKey Vault (directo)

Regla simple: si el valor por sí solo da acceso a algo, va a Key Vault. Si solo controla comportamiento, va a App Configuration. Anti-patrón común: guardar secretos directo en App Config "porque es más fácil" — se pierde auditoría, HSM y rotación automática.
