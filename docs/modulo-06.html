Implement data operations in Azure Managed Redis

Redis como cache: patrones de uso, tipos de dato, expiración e invalidación.

Ver módulo en Microsoft Learn ↗

Tres patrones de cache clásicos

  • Data cache (cache-aside) — se carga solo lo que se pide; si no está en cache (miss), se busca en la DB y se guarda para la próxima.
  • Content cache — fragmentos de UI que casi no cambian (headers, menús), acceso sub-milisegundo.
  • Session store — la cookie solo guarda un ID; los datos de sesión completos viven en Redis, no en la cookie (que viaja en cada request).

Elegir el tier

TierRatio memoria:vCPU
Memory Optimized8:1 — dev/test, cargas livianas de cómputo
Balanced4:1 — la mayoría de workloads
Compute Optimized2:1 — máximo throughput
Flash Optimized (preview)Mueve datos fríos a NVMe — datasets grandes más baratos

Conectar

⚠️ Puerto 10000 en Azure Managed Redis — distinto del 6380 de Azure Cache for Redis "clásico".
r = redis.Redis(host=host, port=10000, ssl=True, decode_responses=True, password=key)

En producción, preferir Microsoft Entra ID (paquete redis-entraid) sobre password estático.

Tipos de dato básicos

  • String — SET/GET, texto o binario.
  • Hash — campos dentro de una key (ej. perfil de usuario); más eficiente en memoria que keys separadas.
  • List — colección ordenada, para colas/feeds (LPUSH/RPOP).
  • Contadores atómicos — INCR/DECR, sin condiciones de carrera; ideal para rate limiting.

Expiración e invalidación

r.setex('session:abc123', 60, 'user_data') # valor + TTL en un solo paso r.expire('user:1002:preferences', 3600) # TTL sobre una key existente

TTL == -1: existe pero sin expiración. TTL == -2: no existe. Elegir el TTL según qué tan rápido cambia el dato: 1-5 min (muy volátil) hasta 24h+ (referencia estática).

⚠️ Nunca usar KEYS en producción (bloquea el server) — para invalidar por patrón, iterar con SCAN.

Implement event messaging with Azure Managed Redis

Pub/Sub para difundir eventos, Streams para colas de trabajo confiables — no son intercambiables.

Ver módulo en Microsoft Learn ↗

Pub/Sub: difusión, no cola

At-most-once, sin persistencia: si un subscriber está desconectado, pierde el mensaje para siempre. Cada mensaje llega a todos los subscribers activos del canal — por diseño.

redis_client.publish('ai:models:updated', 'v2') pubsub.subscribe('ai:models:updated')

Ideal para: invalidar cache en todas las instancias a la vez, notificar cambios de config — no para repartir trabajo.

Streams: cola de tareas confiable

A diferencia de Pub/Sub, los mensajes persisten y se puede confirmar su procesamiento. Ideal para encolar requests de inferencia sin bloquear la API.

redis.xadd('ai:inference:queue', {'prompt': p, 'model': m}) tasks = redis.xreadgroup('workers', worker_id, {'q': '>'}, count=5) redis.xack('ai:inference:queue', 'workers', task_id)

Recuperar tareas colgadas

Si un worker crashea a mitad de una tarea, esta queda "pending" (no confirmada). XPENDING la detecta y XCLAIM se la reasigna a otro worker sano — sin escribir lógica de retry a mano.

⚠️ Los streams no expiran solos — hay que hacer XTRIM o pasar maxlen en XADD, o la memoria crece indefinidamente.

¿Cuál uso? Broadcast vs distribución coordinada

Pub/Sub → Broadcast

3 workers suscritos al mismo canal = los 3 procesan el mismo mensaje (triplicás cómputo). Bueno cuando eso es justo lo que querés (invalidar cache en todas las instancias).

Streams + Consumer Group → Coordinado

3 workers leyendo del mismo grupo = cada mensaje va a uno solo. Escalás agregando workers sin cambiar código — Redis reparte solo.

Muchas arquitecturas usan ambos: Streams para encolar el trabajo real, Pub/Sub para avisar en tiempo real que "algo pasó" (ej. a un WebSocket).

Implement vector storage in Azure Managed Redis

RediSearch convierte Redis en una base vectorial — útil cuando ya usás Redis como cache y no querés sumar otro sistema.

Ver módulo en Microsoft Learn ↗

Crear el índice vectorial

VectorField("embedding", "HNSW", { "TYPE": "FLOAT32", "DIM": 1536, "DISTANCE_METRIC": "COSINE" })

Al crear el índice con un prefix (ej. doc:), Redis indexa automáticamente cualquier vector que guardes bajo esas keys — sin paso de indexado aparte.

FLAT vs HNSW

FLAT

Fuerza bruta, 100% exacto. Bien para <10.000 vectores o desarrollo.

HNSW

Grafo aproximado, 95-99% recall, consultas <10ms incluso con millones de vectores. Default para producción.

Métrica de distancia

MétricaUsar para
COSINEEmbeddings de texto (OpenAI, Cohere) — el estándar
L2Embeddings de imagen / datos espaciales
IPSolo si tus vectores ya vienen normalizados

Queries: KNN, híbrida y por rango

*=>[KNN 5 @embedding $vec AS score] @category:{docs}=>[KNN 3 @embedding $vec AS score] -- híbrida @embedding:[VECTOR_RANGE 0.2 $vec] -- por umbral

EF_RUNTIME controla cuánto explora el grafo HNSW en esa query puntual — default 10 (rápido), subir a 100-200 si necesitás más precisión.

Hash vs JSON para guardar el vector

HashJSON
MemoriaMenor (bytes binarios)Mayor (array + overhead)
VelocidadMás rápidaUn poco más lenta
EstructuraSolo campos planosObjetos anidados, varios vectores por doc

Para la mayoría de casos de similarity search con metadata simple, Hash es la opción por defecto.
