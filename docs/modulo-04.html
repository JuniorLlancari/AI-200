1

Build queries for Azure Cosmos DB for NoSQL

Modelo de datos, conexión con el SDK, operaciones CRUD y consultas SQL sobre documentos.

Elegir la partition key

La decisión de diseño más importante: debe existir en todo documento y tener alta cardinalidad (muchos valores distintos). Un userId suele funcionar bien; un booleano isActive crea una "hot partition" con solo 2 valores posibles.

No se puede cambiar después de crear el container — hay que migrar los datos a uno nuevo.

Throughput: Request Units (RU/s)

Todo consumo (leer, escribir, query) se mide en RUs — una métrica unificada de CPU/memoria/IOPS. Un point read de 1 KB cuesta ~1 RU; un write, 5-10 RUs; una query cross-partition puede costar cientos.

Manual

RU/s fijas que vos definís. Mínimo 400 RU/s.

Autoscale

Escala entre 10% y 100% del máximo configurado según demanda — ideal para tráfico de inferencia impredecible.

Conectar con el SDK

El CosmosClient maneja pooling de conexiones — reusar una sola instancia (patrón singleton) en toda la app, nunca crear uno por request.

Account key

Secreto compartido, acceso total. Simple para dev, riesgoso en producción.

Microsoft Entra ID (RBAC)

Roles como Cosmos DB Built-in Data Reader/Contributor, vía DefaultAzureCredential. Recomendado en producción.

Point read vs Query

Si conocés el id y la partition key, un point read (read_item) es lo más barato posible (~1 RU) — va directo a la partición correcta sin parsear ninguna query.

Una query con filtros es más flexible pero más cara, sobre todo si no incluye la partition key (cross-partition: abanica a todas las particiones).

item = container.read_item(item="product-123", partition_key="electronics")

Escribir: create / upsert / replace

  • create_item — falla (409) si ya existe el id+partition key.
  • upsert_item — crea o reemplaza sin quejarse. Común para cachear resultados de un modelo.
  • replace_item — requiere que exista; soporta concurrencia optimista vía _etag: si alguien más modificó el documento mientras tanto, falla en vez de perder ese cambio.

Consultar con SQL

Sintaxis similar a SQL pero pensada para JSON. Siempre usar queries parametrizadas (@param) — evita inyección y permite cachear el plan de ejecución.

SELECT p.id, p.name, p.price FROM products p WHERE p.categoryId = @category AND p.price < @maxPrice

Funciones útiles: CONTAINS/STARTSWITH para texto, ARRAY_CONTAINS y JOIN para arrays, COUNT/AVG/MIN/MAX para agregados, y SELECT VALUE para devolver valores planos en vez de objetos envueltos.

Implement vector search on Azure Cosmos DB for NoSQL

Guardar embeddings junto a los datos de negocio (sin base vectorial aparte), buscar por similitud y mantenerlos sincronizados.

Vector policy (inmutable)

Se define al crear el container, y ya no se puede cambiar: path del embedding, dimensions (debe matchear tu modelo, ej. 1536 para text-embedding-ada-002), dataType y distanceFunction.

{"path": "/embedding", "dataType": "float32", "distanceFunction": "cosine", "dimensions": 1536}

Función de distancia

Cosine

Ángulo entre vectores. Ideal para embeddings de texto (Azure OpenAI). Rango -1 a +1.

Dot product

Igual que cosine si los vectores están normalizados, pero un poco más rápido de calcular.

Euclidean

Distancia en línea recta. Menos común para texto.

Tipos de índice vectorial

TipoCuándo
flatDatasets chicos, 100% recall, máx. 505 dimensiones
quantizedFlat~1.000-50.000 vectores por partición, comprime para ganar velocidad
diskANNDatasets grandes (millones), aproximado pero muy rápido

quantizedFlat y diskANN necesitan al menos 1.000 vectores para ser efectivos — con menos, cae a full scan.

Buscar por similitud

SELECT TOP 10 c.id, c.title, VectorDistance(c.embedding, @queryVector) AS Score FROM c ORDER BY VectorDistance(c.embedding, @queryVector)

Siempre con TOP N — sin límite, intenta comparar contra todo el container. Para RAG, 5-10 resultados alcanza; más contexto no siempre mejora la respuesta del LLM y sube el costo en tokens.

Filtrar + búsqueda híbrida

Combinar WHERE con VectorDistance filtra por categoría/fecha/permisos antes de rankear. Cuando hace falta también match exacto (ej. un código de error), Reciprocal Rank Fusion (RRF) combina similitud semántica + full-text score:

ORDER BY RANK RRF( VectorDistance(c.embedding, @queryVector), FullTextScore(c.content, @term))

Change feed: embeddings siempre al día

El change feed es un log ordenado de inserts/updates. Con un trigger de Azure Functions, cada vez que un documento cambia, se regenera su embedding automáticamente — sin polling manual.

Requiere un lease container aparte para llevar el checkpoint de qué ya se procesó (y repartir particiones entre varias instancias). La lógica debe ser idempotente: reprocesar el mismo cambio dos veces no debería romper nada.

Optimize query performance for Azure Cosmos DB for NoSQL

Índices a medida, menos RUs por query, y el nivel de consistencia correcto para cada caso.

Por defecto, indexa todo

Cada container nuevo indexa automáticamente todas las propiedades con range indexes — cómodo al empezar, pero cuesta storage y RUs de escritura de más si tenés campos grandes que nunca filtrás (como el content completo o el propio embedding).

Importante: la partition key no se indexa sola si excluís todo por defecto — hay que incluirla a mano si filtrás por ella.

Indexado selectivo

{ "includedPaths": [{"path": "/category/?"}, {"path": "/uploadDate/?"}], "excludedPaths": [{"path": "/*"}] }

Excluí todo (/*) y sumá solo lo que realmente filtrás/ordenás. El embedding siempre debe ir excluido del range index — usa el vector index, no el normal.

Composite indexes

Un ORDER BY con 2+ propiedades requiere un composite index que matchee el orden exacto. Para filtro+orden combinados, poner las igualdades primero y como máximo un filtro de rango al final:

"compositeIndexes": [[ {"path": "/category", "order": "ascending"}, {"path": "/uploadDate", "order": "descending"} ]]

Tuple indexes para arrays

Cuando un documento guarda chunks (ej. chunks: [{position, text, tokens}]) y filtrás por varias propiedades del mismo elemento a la vez, un tuple index indexa esa combinación en vez de cada propiedad por separado.

Write-heavy vs Read-heavy

Write-heavy

Ingesta masiva, updates frecuentes → minimizar índices, cada uno suma latencia de escritura.

Read-heavy

Muchas búsquedas de usuarios → indexar a fondo vale la pena, el ahorro en RUs de lectura compensa.

La mayoría de apps de IA son read-heavy: se ingesta en batch, pero se consulta todo el tiempo.

Niveles de consistencia

NivelGarantíaCosto lectura
StrongSiempre el último write confirmado2× RU (lee 2 réplicas)
Bounded stalenessAtraso máximo de K versiones o T segundos2× RU
Session (default recomendado)"Read-your-writes" dentro de tu propia sesión1× RU
Consistent prefixNunca ves los writes fuera de orden1× RU
EventualSin garantías de orden ni frescura1× RU

Session es el punto justo para la mayoría de apps: un usuario que sube un documento y lo busca al toque, lo ve — sin pagar el 2× de Strong. Para vector search puro, Eventual suele alcanzar.
